<h1 align="center">DeepSeek-V4.1-Flash on 4x DGX Spark — tuned TP4 profile</h1>

<p align="center">A measured TP4 serving profile for <a href="https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash">deepseek-ai/DeepSeek-V4.1-Flash</a> (native weights, SGLang, DSpark) on four NVIDIA DGX Spark (GB10) nodes, built on top of the MiaAI-Lab recipe.</p>

> [!IMPORTANT]
> **As of 2026-11-14 we recommend [pico-dgx-ds4](https://github.com/Picom-code/pico-dgx-ds4) for DeepSeek-V4.1-Flash on four DGX Sparks.**
> It runs its own C++/CUDA engine (dsgb10, by Andy Shu, [blaesus/dsgx10](https://github.com/blaesus/dsgx10); multi-user and 1M context by Pico) on the checkpoint's native weights, and on our fleet it beat this recipe's v2.7.7.
> Same day, same checkpoint (1017 abliterated), same switch, [speedbench](https://github.com/knapcio/speedbench) full mode with thinking off:
> c1 **108.4** vs 94.1 tok/s (+15 %), per stream at c4 / c8 / c16 **+26 / +20 / +13 %**, cold prefill **~9.5k** vs 6.7k tok/s at 131K, qeval 71/75 on both with the same four misses.
> We ran pico's lossless build (its README's arguments without the lossy `DSGB10_OEA`) over our MikroTik switch with `DSGB10_RING_DIRECT=2`; no ring cabling is needed. Our four Sparks serve it in production since 2026-11-14.
> Where this recipe still leads: with 16 concurrent requests it delivered more total tokens per second on pico's own `bench.py` (~390 vs ~320, 16 distinct prompts), and its median time to first token under load was about half (c16: 478 vs 981 ms).
> This repository stays available and gets bug fixes, but no further speed work.

## Current results

**v2.7.7** (2026-11-13, in production on the four Sparks from 2026-11-13 04:39 to 2026-11-14 11:35) is v2.7.6 plus one lossless decode change in the production profile: single-request (c1) draft steps read the draft LM head from a 4-bit MXFP4 copy instead of the fp8 twin (`DSV41_DRAFT_HEAD_FP4=1`; 88 MB per rank read per draft call instead of 166 MB, through a CUDA-core GEMV; batched drafts keep the fp8 twin). Only the draft reads it: the target's logits and every emitted token are unchanged, and only the draft acceptance can move. The change does not run in prefill: cold prefill x1.004 at 64K, x1.001 at 131K and x1.008 at 1M of the controls' mean, a cold 388K prompt's first token in 56.5 s against 56.4-56.9 s. Outputs: qeval 71 / 71 / 71, all 75 T = 0 qeval prompts inside the controls' bracket, KLD 0.009 short / 0.005 long (limit 0.035), reasoning length identical. The head's memory low-water is 5.26 GiB against 5.22-5.35 GiB (the MXFP4 copy is 84 MiB per rank). Speculative decoding makes tok/s depend on the generated text, so other DeepSeek releases give somewhat different numbers on the same prompts.

## What this profile changes

Relative to the upstream TP4 example, all of it in `.env.tp4.example` plus gated adapters:

| Setting | Upstream | Here | Why (measured) |
|---|---|---|---|
| `EP_SIZE` | 4 | **1** | On the production image (`DSV41_MOE_B12X_NEXT`): every rank streams a 576-wide slice of every touched expert, so no expert group waits for the other at the MoE all-reduce. The base and canary images stay at `EP_SIZE=2` (FlashInfer's MXFP4 MoE needs the per-rank width to be a multiple of 128), which already halves the EP4 straggler wait: NCCL time per step 16.5 → 10.2 ms |
| `DSV41_CACHE_GIB`/`WAYS` | 0/4 | **4/16** | Engram rows do repeat (bigram/trigram heads): 67–76 % hit rate, 4x fewer NVMe reads; 16 ways are free |
| `--min-free-slots-delay 1` | on | on | Without it the admission delayer never fills the last slot |
| `--enable-deepseek-v4-fp4-indexer` | off | on | no effect on V4.1: the model has no ratio-4 layers and its only indexer is fp4 by design; a four-boot A/B (off/on/off/on) gave identical greedy output and speed. Kept only so the argument line matches earlier runs |
| `DSPARK_BLOCK_SIZE` | 3 | **5** | k=3 is a 3-node prose result; on TP4 k=5 wins on code by ~10 % and ties on prose |
| `MAX_RUNNING_REQUESTS` | 8 | **16** | CUDA graphs to bs 16 cost ~5.6 GB and add a c16 tier (+64 % aggregate over c8) |
| `CHUNKED_PREFILL_SIZE` | 1024 | **4096** | Safe only together with the indexer backport below |
| `DSV41_SHARED_PAD_K=1` | – | **on** | Pads the shared expert's K 576 → 640 so it stops falling off the b12x MXFP8 kernel: −0.9 ms/step, bit-identical |
| `DSV41_INDEXER_CHUNKED=1` | – | **on** | sglang#39187: indexer logits scored in ≤ 2 GiB row chunks, tail-only candidate masks; 262k cold prefill keeps ≥ 7 GiB free on the head |
| prefill TP split (`SPARK_PREFILL_TP_SPLIT=1`, canary images) | – | **on** | SG18: the dense prefill indexer's query rows are partitioned across the four ranks from 32k context; each rank scores a quarter, the top-k and candidate block ids are all-gathered as ints. sparkDash prefill 128k 3499 → 4364, 262k 2701 → 3893 |
| `--enable-cache-report` | off | **on** | `usage.prompt_tokens_details.cached_tokens` on every response (also in streaming `usage`), so clients can see prefix-cache hits |

Everything else (memory fraction 0.80, 8M-token KV pin, 1M context, NFS/Engram layout, the OpenAI serving fixes) is upstream's.

## Quick start

Same launcher as upstream; read [`docs/README-upstream.md`](docs/README-upstream.md) first for the fleet setup (NFS share, Engram packing, fabric). `pack` needs the checkpoint, so download it before the first `pack`.

The base image is pinned by digest (`lmsysorg/sglang:dev-dsv41@sha256:3dbc3130…`, the multi-arch index this recipe was built and tested on). The `dev-dsv41` tag itself moves upstream, and the build-time patches check the exact files of this base, so do not override `BASE_IMAGE` with the bare tag. Build `Dockerfile.canary-roce` (the production image) as below; the plain `Dockerfile` is the old base-image path and its in-image tests expect the canary SGLang tree, so it is not a supported TP4 build.

## Measuring

- Bench with [speedbench](https://github.com/knapcio/speedbench) (full, load and longctx modes), never with a hand-rolled loop; discard the first run after a boot (cold Engram row cache, first-run warm-up).
- Any `#running-req` in the engine log above the concurrency being benched means foreign traffic landed in the window.
- A dashboard polling `nvidia-smi` every 2 s on every node costs ~0.6 ms per decode step; poll every 10 s (`POLL_INTERVAL_GPU=10000`, `POLL_INTERVAL_BANDWIDTH=10000`).
- Fixed benchmark prompts are greedy: a change that alters rounding can flip a near-tie early in the 256 tokens and move c1 by ±10 % without changing speed. Kernel A/Bs here use step time on several prompts as well.
- Release gate tools: `scripts/qeval.py` (75 tasks), `scripts/ds_gate.py kld` (greedy-continuation KL against a reference stack, long and short panels) and `ds_gate.py tscan` (T > 0 garble scan), `scripts/prefix_scan.py` (shared long prefix at c8, cold vs warm, plus cold-vs-warm logprob drift on full and mid-document cache hits).
- Greedy text equality is not a correctness gate for prefill changes: identical cold prompts of ~70k tokens produce different greedy continuations run to run. Correctness of the backports rests on the bitwise CPU tests, the needle tests and qeval.

## Known limits

- The numbers above are on a switched RoCE fabric. On a switchless ring RoCEnante needs a path to the opposite node, built in the neighbours' ConnectX-7 hardware ([docs/switchless-ring.md](docs/switchless-ring.md#rocenante-on-the-ring-hardware-forwarded-opposite-node-paths)); without it the collectives go through NCCL and decode is slower. Prefill is lower on a ring either way (one-link bisection).
- The EP1 production line needs the `Dockerfile.canary-roce` image (it carries `runtime/b12x_next`). The routed MoE on b12x is numerically equivalent to FlashInfer's, not bit-identical (relative error against an fp32 reference 4.5–4.8 % for both); qeval and the needle tests are unchanged.
- Prompt-token logprobs and all-token hidden states are not available: `boot.py` launches with `--enable-decoder-swa-bounded-replay` (Mia's recipe), so the 19 layers after the last KV-source layer run only over the last 128 rows of each prefill, and such requests get HTTP 400. Output logprobs work. Cache hits are exact: a hit that lands on a prefill chunk boundary gives bit-identical logprobs to a cold request; a hit elsewhere computes the tail with a different batch shape, which moves low-probability logprobs by the same amount as the run-to-run nondeterminism of cold prefills on some prompts (`scripts/prefix_scan.py`, `docs/results/validation-20260929-v23.txt`).
- The full KV pool is pinned at 8,541,952 tokens (fraction 0.85, the same pin since v2.6.5), which leaves the head less free host memory: on v2.6.5 its lowest MemAvailable was 5.72 GiB in the memory ladder with eight 1M-token prompts resident at once, a cold 1M prefill and a long-prompt soak (2 NVRM out-of-memory log lines on two workers in that cell), against 8.9-9.3 GiB with a 5.13M pool at 0.78. The ladder was not repeated on v2.7, whose window cache is ~0.4 GiB per rank smaller; in the v2.7.5 release gate the head's low-water was 6.19 GiB (v2.7.4 controls 8.48 / 8.36 GiB), lower by the 2.03 GiB per rank the scale codes keep beside the native scales (`DSV41_MOE_SCALE_CODES` unset returns it), and in the v2.7.6 release gate 5.19 GiB (v2.7.5 controls 5.76 / 5.73 GiB), lower by the greedy flavours' second capture of the draft and verify graphs (`DSV41_GREEDY_NOGATHER` unset returns it), and in the v2.7.7 release gate 5.26 GiB (v2.7.6 controls 5.22 / 5.35 GiB; the MXFP4 draft-head copy is 84 MiB per rank); the fraction 0.85 also leaves the 8192-token prefill chunk less spare memory. Measured only for the ladder's and the gate's workloads. If the head runs short, 8,000,000 at 0.85 (low-water 5.96 GiB in the ladder) is the next step down, and the v2.6.4 values (see [Rollback](#rollback)) give ~3.4-3.7M tokens. Since v2.6.4 the SWA prefix-tail reserve is 384 tails (182,784 slots, ~3.7 GiB per rank in v2.7's 528-byte layout, ~4.1 GiB before); a session that forks from an older turn boundary (an edit or rewind) falls back further under SWA pressure than with 128, because superseded checkpoints are evicted first. Never raise the chunk to 16384: at 1M it took a worker to 2.5 GiB available and hung the node on another fleet.
- v2.7 is a numerics change against v2.6.5 (the window keys' RoPE part is stored in FP8, as in DeepSeek's reference): at T = 0 its text differs from v2.6.5's on some prompts (26 of the 74 stable qeval prompts in the release gate), within KLD 0.011 short / 0.006 long against v2.6.5 (limit 0.035) and with the same qeval score, and per-category speed moves with the text (code -3.4 %, structured / agentic / multilingual +2 to +3 % in the gate). Cold prefill from 64K to ~400K context is ~1.7 % slower than v2.6.5 (FlashInfer 0.7.2's BF16 sparse-MLA prefill kernel); a cold 1M prompt is close to parity.
- The sparse-MLA calibration is frozen: the image ships FlashInfer 0.7.2's own calibration of the four V4.1 TP4 request shapes on a GB10 (`files/fi-autotune`), measured only on this TP4 profile, and a missing file refuses the boot. `DSV41_V41_CALIBRATION=inprocess` restores FlashInfer's in-process calibration for diagnostics only: after the CUDA-graph capture it faulted every cold boot on the four Sparks.
- One of the eight v2.4 boots on 2026-10-12 hung in the server's internal warm-up request and was restarted by the boot timeout; the retry and the seven other boots were clean.
- Single-stream prose speed is bounded by DSpark acceptance (~3 accepted tokens per step on prose against ~6 on code); no configuration changes that.
- The fast loader leaves the KV pool 3–13 % smaller than the stock loader (6.7–7.3 M vs 7.5–7.8 M tokens) and more variable between boots; `DSV41_FAST_LOAD=0` restores it at ~220 s per boot ([docs/fast-load.md](docs/fast-load.md)).
- RoCEnante is a new transport in the decode path; b12x has one open report of a rank wedging under long mixed-context traffic on an earlier revision ([b12x#313](https://github.com/local-inference-lab/b12x/issues/313)). The overlay's result-boundary health check fails the step instead of hanging, and NCCL is one env change away.
- The decode yield (`DSV41_DECODE_YIELD=33`) lengthens a long prompt's prefill while other streams decode (x1.47 at 500K beside two streams). A short request (<= 8192 fresh tokens) that arrives during a yield waits for the yield to end before its solo pass, and a longer follow-up queued behind the long prompt waits for the whole, longer prefill. Its cost model was fitted to one production boot's log; the share reached is what the fleet measurement shows, not a guarantee for other batch sizes.
- The lost-resume-point replay (`DSV41_SWA_CONE_REPLAY`) needs the whole 8192-token chunk budget in its first step: next to a co-batched prefill, or with a smaller chunk, it falls back to the stock re-prefill (a `DSV41_SWA_CONE revert` line). An internal invariant violation stops the engine on every rank rather than serving a replay outside its exactness argument. Its engine functions are sha256-pinned; on drift it does not install (stock behaviour, logged).
- The two-shot all-reduce is measured on a switched fabric only and is not available with `DSV41_ROCE_RING=1`; on the ring leave `DSV41_ROCE_TWOSHOT` unset.
