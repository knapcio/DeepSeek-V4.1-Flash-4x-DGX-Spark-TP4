<h1 align="center">DeepSeek-V4.1-Flash on 4x DGX Spark — tuned TP4 profile</h1>

<p align="center">A measured TP4 serving profile for <a href="https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash">deepseek-ai/DeepSeek-V4.1-Flash</a> (native weights, SGLang, DSpark) on four NVIDIA DGX Spark (GB10) nodes, built on top of the MiaAI-Lab recipe.</p>

## Current results

**v2.6.5** is v2.6.4 plus the V4.1 FP4 KV layout in the production profile (`DSV41_KV_LAYOUT=v41c DSV41_V41C_ARM=1 DSV41_V41C_READER=native`, "v41n": the compressed KV records take 912.25 instead of 1670.75 bytes per token and are read in place, outputs in the V4 exactness class), with the full KV pool pinned at `MAX_TOTAL_TOKENS=8541952` and `MEM_FRACTION_STATIC=HEAD_MEM_FRACTION_STATIC=0.85`: **8,541,952 tokens, +69 % against v2.6.2's ~5.06M** (x2.3-2.5 against v2.6.4's 3.44-3.70M), eight 1M-token contexts at once instead of three. The trade-off is the head's free host memory: its lowest MemAvailable was 5.72 GiB in the memory ladder on the four Sparks (eight 1M-token prompts resident at once, a cold 1M prefill and a long-prompt soak) against 8.9-9.3 GiB with a 5.13M pool at fraction 0.78, and 7.15 GiB in the release gate (v2.6.2 controls 8.77 / 10.22). The rollback is the v2.6.4 profile values (see [Rollback](#rollback)). It also adds `DSV41_TOKENIZER_HEAP=trim2` (the head's tokenizer process returns the GiBs of free heap that back-to-back long prompts leave behind; allocation only) and the fix for #66 (a loop-aborted request ends as a named error; broken tool calls in the history no longer get HTTP 400). Speed is unchanged within the gate's noise (greedy c1 +1.1 % / +1.3 % against the two v2.6.2 control boots).

Since v2.6.4 the profile has a decode attention that reads the sliding-window cache in place instead of copying it into smaller pages first (bit-identical outputs, greedy c1 decode about 1.5 % faster in two in-boot A/Bs) and a decode yield: while one prompt prefills in chunks, the other running streams keep about 40 % of their decode rate instead of 8 %, and that prompt's first token comes about 1.5x later. It also keeps idle agent sessions' prefix-cache resume points (superseded SWA checkpoints are evicted first and the SWA pool holds 384 prefix tails instead of 128: resumed 300-330K-token sessions answered in 3.9-6.5 s instead of 61-64 s; the larger SWA reserve is paid from the full KV pool), and a resume point that is evicted anyway costs a one-chunk replay (~2 s) instead of a whole-context re-prefill (details in [CHANGELOG.md](CHANGELOG.md)). The default weights are the official checkpoint (below); the v2.6.5 release gate and the per-category tables were measured on its abliterated variant, which `.env.tp4.example` keeps as an optional profile. Setup: image `Dockerfile.canary-roce` with this release's adapters and RoCE runtime (SGLang `dsv4.1` `f80c91a4b` + the credited backports, without #45251), the "Production profile" block of [`.env.tp4.example`](.env.tp4.example) with `EP_SIZE=1`, 1M context, checkpoint [`mrfakename/DeepSeek-V4.1-Flash-1017-abliterated`](https://huggingface.co/mrfakename/DeepSeek-V4.1-Flash-1017-abliterated) at `517efab`, GPU clock capped at 2200 MHz, fresh boots with the host memory compacted first and the first run after each boot discarded. Speculative decoding makes tok/s depend on the generated text, so other DeepSeek releases give somewhat different numbers on the same prompts.

## What the production profile runs

| Layer | Setting | What it does |
|---|---|---|
| Image | `Dockerfile.canary-roce` | upstream SGLang `dsv4.1` branch at `f80c91a4b` + credited #41303/#42901 backports + rhys101's RoCEnante overlay + all adapters; since v2.6.3, FlashInfer 0.6.18's b12x dense MXFP8 GEMM gets the proxy fence of [flashinfer#7676](https://github.com/flashinfer-ai/flashinfer/pull/7676) at build (found and fixed upstream by Thireus, [flashinfer#7675](https://github.com/flashinfer-ai/flashinfer/issues/7675)): without it a tile can read the next pipeline stage's data under concurrent GPU work, reproduced on GB10 (26 of 2,304 eager prefill calls wrong with a second stream busy, 0 with the fence); quiet outputs unchanged, speed x1.0005; each rank logs `DSV41 b12x dense GEMM fence (FlashInfer #7676): present` at boot |
| Slots | `MAX_RUNNING_REQUESTS=16` | adds the c16 tier |
| Experts | `EP_SIZE=1`, `DSV41_MOE_B12X_NEXT=1`, `DSV41_MOE_B12X_NEXT_DETERMINISTIC=1` | every rank holds a quarter of all 384 experts and the routed MoE runs on b12x main: no expert-group straggler at the MoE all-reduce (all-reduce 5.9 → ~2.6 ms per step), MoE time unchanged. The deterministic reduction (per-slot buffer and a fixed-order sum instead of atomics) costs nothing measurable and makes greedy output bit-identical run to run; its <= 8-row plans use a Triton route planner and zero the barrier words in one fill (bit-identical to b12x's internal planner) |
| Engram | `DSV41_CACHE_GIB=4`, `DSV41_CACHE_WAYS=16`, `DSV41_ENGRAM_PREFETCH=1`, `DSV41_ENGRAM_KEEPALIVE_MS=25` (default) | row cache (67–76 % hits) and row lookups on a side stream, rows bit-identical. While lookups arrive, one 4 KiB read every 25 ms keeps the NVMe drive out of its power-saving states: at c16 the drive slept between steps and each step's row reads paid ~10 ms to wake it (c16 step 149 → 140 ms, +5-6 % c16 aggregate; c1 unchanged) |
| Draft | `DSPARK_BLOCK_SIZE=5`, `SGLANG_DSPARK_FOLDED_SAMPLING=2` | k=5 wins on code, ties on prose; sampled requests stay in the CUDA graph |
| Draft sampling | `DSV41_DRAFT_TAU=0.7`, `DSV41_BLOCK_VERIFY=1` | sharper draft proposals and block verification for sampled rows, both exact in distribution. | Sampled verify | `DSV41_BLOCK_VERIFY_FOLD=1` | the block verification of sampled rows in three Triton kernels instead of ~55 eager torch launches after the verify graph; the three vocabulary-wide reductions stay torch's own operations on the same tensors, so the accepted length and correction token are bit-identical to the torch path for the same random draws (exact in distribution, like block verification itself); greedy requests never take this path. Since v2.6.3: sampled speedbench c1 +0.8 / +1.4 % and c4 +0.5 / +0.7 % against the two v2.6.2 boots of the release gate. Block verification: Sun et al., ICLR 2025; the three-kernel fold is ours |
| Verify length | `DSV41_VERIFY_CAP=conf:0.1`, `DSV41_ROUTER_LIVE=1` | verifies only the drafts the confidence head expects to survive; the other verify rows reuse the anchor row's experts inside the router kernel, so they read no extra weights; greedy outputs identical |
| Kernels | `DSV41_SHARED_PAD_K=1`, `DSV41_WO_A_W8=1`, `DSV41_WO_A_W8_MID=1`, `DSV41_WO_A_W8_DROP=1`, `DSV41_DRAFT_HEAD_FP8=1` | shared expert kept on the b12x kernel; `wo_a` and the draft LM head read exact fp8 twins of their weights |
| Replicated linears | `DSV41_REPLICATED_SPLIT=wqkv_a,engram.wkv`, `DSV41_DRAFT_MAIN_PROJ_SPLIT=1`, `DSV41_SPLIT_COMPACT_GATHER=1` | layers every rank computed in full are split by columns across ranks and all-gathered; enabled only where bit-identical on all ranks. A rank with a narrower slice runs its GEMM on a window of the widest slice's width, so no pad precedes the gather, and with the compact gather each rank sends only its own columns, which RoCEnante writes in place (no pad, reorder or cat; checked byte for byte against the old path per layer and row count at boot) |
| Transport | `SGLANG_ROCE_ALLREDUCE=1`, `SGLANG_ROCE_MAX_SIZE=2097152`, `DSV41_ROCE_GATHER=2097152`, `B12X_ROCE_HCA=rocep1s0f0,roceP2p1s0f0` | TP all-reduces and all-gathers up to 2 MiB over the one-shot RDMA kernel on both rails |
| Two-shot all-reduce | `DSV41_ROCE_TWOSHOT=1`, `DSV41_ROCE_TWOSHOT_ROWS=18`, `B12X_ROCE_PIPE_BLOCKS=4`, `B12X_ROCE_PIPE_CHUNK_BYTES=65536` | all-reduces of 18 rows or more (the wide verify and draft steps at higher concurrency) take a pipelined two-shot path: each rank sends its quarter to the row owner, which sums the four partials in FP32 in rank order and rounds once, as the one-shot does, then the reduced rows are gathered back. Half the bytes on the wire, bit-identical output; smaller all-reduces stay one-shot. c16 +3.7 % alone (+4.9 % with the two prefill switches below), c1 / c4 unchanged |
| Idle transport | `DSV41_ROCE_IDLE_PARK=1` | while the engine is idle, the RDMA proxy thread of each rank blocks on a futex instead of polling every 20 us; the scheduler wakes it before every forward, and a parked proxy re-checks its doorbell every 20 ms, so a missed wake costs latency, never correctness. Since v2.6.3: idle proxy CPU summed over the four nodes 9.6 % → 1.75 % of a core in the release gate, speed and greedy outputs unchanged. Idea: uchkw; implemented independently |
| Prefill | `CHUNKED_PREFILL_SIZE=8192`, `MEM_FRACTION_STATIC=HEAD_MEM_FRACTION_STATIC=0.85` (with the pool pin, since v2.6.5; 0.78 before), `DSV41_INDEXER_CHUNKED=1`, `SPARK_PREFILL_TP_SPLIT=1` | bounded indexer transient (sglang#39187) plus the SG18 row split across ranks from 32k context; 8192-token chunks are 17-28 % faster on 400K-1M cold prompts. Unpinned, the fraction 0.78 gave back the ~3 GiB the larger chunk costs at 1M (at 0.80 the head dropped to 2.7 GiB available); since v2.6.5 the KV pin, not the fraction, sizes the pool, and 0.85 leaves the chunk less spare memory than 0.78 did: the 1M prefills of the memory ladder and the release gate passed at it |
| Prefill attention pages | `DSV41_PREFILL_NATIVE_EXTRA=1` (since v2.6.2) | SM120 sparse-MLA prefill reads the extra (compressed) cache in SGLang's own 128 / 256-token pages through a module generated from FlashInfer's sources at image build (approved source closure, sha256-pinned .so, no JIT at boot) instead of a persistent 64-token copy of the whole pool: 2.45-2.76 GiB less allocated after pool sizing per node, cold 1M prefill -5 %, bit-identical |
| Decode attention pages | `DSV41_SWA_NATIVE_DECODE=1` (since v2.6.4) | every decode attention call (up to 64 query rows: the DSpark verify and draft forwards) reads the sliding-window cache in SGLang's own 256-token pages; before, each call copied every touched page into four 64-token pages first (43 copy chains per c1 step), because FlashInfer's decode kernel was instantiated for 64-token pages only. Same kernel body at 256-token pages (its address math is generic in the page size), same tactic, same output bits; other shapes keep the copy. Module built at image build (`runtime/flashinfer_v41c`, sha256-pinned .so). Two in-boot A/Bs on the four Sparks: greedy c1 +1.36 / +1.86 %, c4 -0.06 / +0.85 %, sampled c1 -1.95 / +0.79 % (sampled run-to-run spread up to 3 %); T = 0 text identical on every stable prompt. Built on FlashInfer's SM120 sparse-MLA decode kernel; the 256-token instantiation is ours |
| Prefill MoE launch | `DSV41_MOE_LAUNCH_PREPARED=plan` | eager (prefill) b12x MoE launches reuse a launch plan prepared once per launch contract instead of redoing the host-side quant, routing, tile and kernel-lookup decisions on every call; barrier fill, route planner, pointers and stream stay per call, and the plan is dropped on any `B12X_NEXT_*` environment change or kernel-cache change. Same kernels and arguments, bit-identical |
| Prefill indexer | `DSV41_INDEXER_NOSYNC=1` | the eager prefill indexer of the eight index-source layers builds its compressed-slot ids with one device gather and pinned non-blocking copies instead of a per-request `.item()` and a pageable copy (two host syncs per request per layer). Integer ops in the same order, bit-identical. With the MoE launch plan: cold 4k prefill +16 %, 64k +3.4 %, TTFT -4 % (c1 214 → 206 ms, c16 563 → 539 ms) |
| Multi-user | `--prefill-decode-interval 2`, `DSV41_PREFILL_BYPASS=256`, `DSV41_PREFILL_BYPASS_SOLO=1` (since v2.6.2) | a short request that arrives during a long cold prefill is admitted by the bypass scan and decoded between chunks: answered in 4.6 s instead of after the prefill (80 s at 400K); the admission adapter only acts after the engine's own memory check and reads only rank-identical state. Since v2.6.2 it runs in a prefill pass of its own while the long prompt is parked (first token 0.42 s instead of 1.9 s at 93K-128K); the long prompt resumes with the same chunk, so its outputs are those of an idle run |
| Streams during a long prefill | `DSV41_DECODE_YIELD=33` (since v2.6.4) | after each non-final 8192-token chunk of a long prompt with other streams decoding, the next chunk waits until those streams have had decode time worth 33/67 of the chunk's time (an integer cost model of chunk and step times fitted to the production log, no clock, so every rank decides alike; at least the `--prefill-decode-interval` steps, at most 128). Only when the next chunk runs changes: chunk boundaries, batches and outputs are the engine's own. On the four Sparks (two streams on 300K contexts beside a cold 500K prompt): the streams' decode rate during the prefill 0.080 → 0.393 of their rate before it, the 500K prompt's first token x1.47 later; speedbench c1 / c4 unchanged (+0.7 to +1.0 % at share 50). | Tokenizer heap | `DSV41_TOKENIZER_HEAP=trim2` (since v2.6.5) | under back-to-back 200K-900K-token prompts the head's tokenizer process kept GiBs of free glibc heap resident (1.9 → 5-7 GiB in a 15-minute soak on v2.6.4, the head's memory floor). `malloc_trim(0)` after >= 256 MiB of new heap, at most once per 120 s, in a tokenizer gap or at the end of a prompt's tokenization: on the four Sparks the process stayed at 1.0-3.1 GiB (controls 3.9-4.3), 0 of 74 qeval tasks changed, throughput within 1 %; a busy trim pauses token delivery up to ~0.8 s about every 2 minutes while long prompts keep arriving |

| Prefill hc | `DSV41_HC_FUSED=1` | the hyper-connection mix statistics of prefill chunks in one pass over K instead of 80 partial slices: ~1.46 → ~0.83 ms per call at 4096 rows, bit-identical to the stock kernels (checked on the first live call) |
| Prefill sequence parallel | `DSV41_PREFILL_SP=1` | at prefill chunks of >= 2048 rows the per-layer all-reduces become reduce-scatter + all-gather, and the per-row work between them (hyper-connection mixing and norms, the Engram `wkv` projection and gate) runs on each rank's quarter of the rows instead of all four ranks repeating it: prefill ~+20 % from 16k to 262k. Decode is untouched. The partial sums are added in a different order than the all-reduce's (the same kind of change as RoCEnante); `DSV41_PREFILL_SP_EXACT=1` keeps the all-reduce and is bit-identical to the unsharded path (checked op by op on the fleet) for ~+10 %. `DSV41_PREFILL_SP_FP8=1` gathers the attention input of 17 of the 21 full-row layers as the MXFP8 bytes and scales `wqkv_a` would compute itself (checked bit-identical per chunk size on every rank): about half the gather bytes there, +1.5-3 % prefill |
| L2 prefetch | `DSV41_L2_PREFETCH=1`, `DSV41_L2_PREFETCH_WOA=1` | during each RoCE all-reduce and all-gather of a decode step (SMs and DRAM mostly idle for 15-30 us) a side-stream kernel prefetches the first 6 MB of the weights that follow into L2; plans are learned from the warm-up forwards and captured in the CUDA graphs. Data is untouched (outputs bit-identical); decode step -1 ms at c1, +3 % on varied prompts, flat at c16. `WOA` adds a window after `wq_b` that prefetches `wo_a` while the attention core runs: -0.4 ms/step |
| Decode-step sync | `DSV41_SPEC_SYNC_FREE=all` | drops the per-step rank-0 broadcasts whose values are already identical on every rank (the draft token of each Markov step, the verify epilogue's three, verify_cap's live length); the draft noise comes from a counter-based stream every rank computes alike. Audit mode counted 0 rank mismatches in ~60k checks; greedy output byte-identical; -0.53 to -0.59 ms/step in an in-boot A/B (~-0.2 ms across reboots) |
| Decode-step glue | `DSV41_EAGER_GLUE=all` | fewer eager kernels between the draft and verify CUDA graphs (the folded fence's six copies as one, sampling-param staging skipped while unchanged, verify_cap's update inside the draft graph as one kernel); bit-identical, ~-0.1 to -0.2 ms/step |
| Target LM head | `DSV41_CERT_HEAD=1`, `DSV41_CERT_HEAD_M=6,...,48` | greedy verify steps read an 8-bit (MXINT8) screen of the head shard (173 MB instead of 331 MB per rank) with a proven error bound, and compute exactly only the 16-row head tiles that can hold the argmax; the argmax is the stock one (exact kernel bit-identical to the stock matmul, 0 mismatches over 3,355 checked steps), and sampled rows, logprobs, grammar and penalties get the full exact logits. -0.5 ms per c1 step; slower from 10 requests up, so it stops at 8 (M = 48 verify rows); +173 MB per rank |
| Correctness | `DSV41_FOLDED_FENCE=1` | closes the sglang#40919 D2H race on the folded verify path |
| Request guard | `DSV41_REPLAY_GUARD` (default on) | the launch runs SGLang's decoder SWA bounded replay (late layers see only the last window of a prefill), which cannot return prompt-token logprobs; such a request (`/generate` with `logprob_start_len` below the prompt length, `/v1/completions` with `echo` + `logprobs`) used to raise inside the forward and end every rank. It now gets HTTP 400 and the server keeps serving |
| Loop abort | `DSV41_LOOP_ABORT=1`, `DSV41_LOOP_NAMED_EXIT=1`, `DSV41_HISTORY_REPAIR=1` (defaults) | a request whose output cycles (four copies of a ≥ 32-token n-gram, 64 identical tokens or eight identical lines) is ended as an error named `loop_abort: ...` (stream: error event; non-stream: HTTP 500), not as `finish_reason=stop`, so agent clients see a failed step; a broken tool call in the request history is rendered as `{"_unparseable_arguments": <raw>}` instead of HTTP 400 (MiaAI-Lab PR #55 by Alexander Busse (GanyX19); since v2.6.5) |
| Serving | `--enable-cache-report`, `--sleep-on-idle`, `SGLANG_RUST_BUILD_MODE=never` | cached-token usage for clients, idle CPU 47 % → 14 %, avoids a `cargo` hang at start; engine `/metrics` is documented as an opt-in |
| Optional | `DSV41_ENGRAM_DRM_NODE=/dev/dri/card0` | one Engram layer's cache in the GB10 display reservation, ~1.8 GiB more headroom; needs a host change ([docs/display-reserve.md](docs/display-reserve.md)) |

Not used: `DSV41_ADAPTIVE_CHUNK` (superseded by the bounded indexer), `DSPARK_SPS_TABLE` (ignored by `boot.py` because compact ragged verify crashes the Engram path; `DSPARK_SPS_ALLOW_ENGRAM=1` is an explicit future-fix override), NVIDIA's NVFP4 checkpoints ([#64](https://github.com/knapcio/DeepSeek-V4.1-Flash-4x-DGX-Spark-TP4/issues/64)): their routed experts are the official MXFP4 values re-encoded losslessly with twice the scale bytes (about +4 GiB per rank on the GPU and about 6 % more expert bytes read per decode step), and the 76 GiB smaller file comes from the two Engram tables re-quantized from FP8 to FP4, which is lossy and frees nothing here because the engine serves Engram rows from NVMe. Each adapter is described in [docs/adapters.md](docs/adapters.md); the measured effect of each switch is in [docs/history.md](docs/history.md#production-stack-as-of-2026-09-24-with-the-full-rationale-per-switch).

## What this profile changes

Relative to the upstream TP4 example, all of it in `.env.tp4.example` plus gated adapters:

| Setting | Upstream | Here | Why (measured) |
|---|---|---|---|
| `EP_SIZE` | 4 | **1** | On the production image (`DSV41_MOE_B12X_NEXT`): every rank streams a 576-wide slice of every touched expert, so no expert group waits for the other at the MoE all-reduce. The base and canary images stay at `EP_SIZE=2` (FlashInfer's MXFP4 MoE needs the per-rank width to be a multiple of 128), which already halves the EP4 straggler wait: NCCL time per step 16.5 → 10.2 ms |
| `DSV41_CACHE_GIB`/`WAYS` | 0/4 | **4/16** | Engram rows do repeat (bigram/trigram heads): 67–76 % hit rate, 4x fewer NVMe reads; 16 ways are free |
| `--min-free-slots-delay 1` | on | on | Without it the admission delayer never fills the last slot |
| `--enable-deepseek-v4-fp4-indexer` | off | on | no effect on V4.1: the model has no ratio-4 layers and its only indexer is fp4 by design; a four-boot A/B (off/on/off/on) gave identical greedy output and speed. Kept only so the argument line matches earlier runs |
| `DSPARK_BLOCK_SIZE` | 3 | **5** | k=3 is a 3-node prose result; on TP4 k=5 wins on code by ~10 % and ties on prose |

| `DSV41_SHARED_PAD_K=1` | – | **on** | Pads the shared expert's K 576 → 640 so it stops falling off the b12x MXFP8 kernel: −0.9 ms/step, bit-identical |
| `DSV41_INDEXER_CHUNKED=1` | – | **on** | sglang#39187: indexer logits scored in ≤ 2 GiB row chunks, tail-only candidate masks; 262k cold prefill keeps ≥ 7 GiB free on the head |

## Measuring

- Bench with [speedbench](https://github.com/knapcio/speedbench) (full, load and longctx modes), never with a hand-rolled loop; discard the first run after a boot (cold Engram row cache, first-run warm-up).
- Any `#running-req` in the engine log above the concurrency being benched means foreign traffic landed in the window.
- A dashboard polling `nvidia-smi` every 2 s on every node costs ~0.6 ms per decode step; poll every 10 s (`POLL_INTERVAL_GPU=10000`, `POLL_INTERVAL_BANDWIDTH=10000`).
- Fixed benchmark prompts are greedy: a change that alters rounding can flip a near-tie early in the 256 tokens and move c1 by ±10 % without changing speed. Kernel A/Bs here use step time on several prompts as well.
- Release gate tools: `scripts/qeval.py` (75 tasks), `scripts/ds_gate.py kld` (greedy-continuation KL against a reference stack, long and short panels) and `ds_gate.py tscan` (T > 0 garble scan), `scripts/prefix_scan.py` (shared long prefix at c8, cold vs warm, plus cold-vs-warm logprob drift on full and mid-document cache hits).
- Greedy text equality is not a correctness gate for prefill changes: identical cold prompts of ~70k tokens produce different greedy continuations run to run. Correctness of the backports rests on the bitwise CPU tests, the needle tests and qeval.

## Rollback

Every layer is an env change: `EP_SIZE=2` without `DSV41_MOE_B12X_NEXT` returns the routed MoE to FlashInfer, `DSV41_FAST_LOAD=0` restores the stock loader, `SGLANG_ROCE_ALLREDUCE=0` drops the RDMA transport, `SPARK_PREFILL_TP_SPLIT=0` the row split, `IMAGE=dsv41-4x-spark:canary` the RoCEnante overlay, `IMAGE=dsv41-4x-spark:local` the branch; unsetting `DSV41_SPEC_SYNC_FREE`, `DSV41_EAGER_GLUE`, `DSV41_SPLIT_COMPACT_GATHER` and `DSV41_L2_PREFETCH_WOA` turns off the v2.2 decode-step changes, unsetting `DSV41_CERT_HEAD` the v2.3 certified head (`DSV41_REPLICATED_SPLIT_WINDOW=0` and `DSV41_MOE_B12X_NEXT_DET_TRITON=0` the two that are on by default). Unsetting `DSV41_KV_LAYOUT`, `DSV41_V41C_ARM` and `DSV41_V41C_READER` and setting `MAX_TOTAL_TOKENS=8000000` with the fraction 0.78 returns v2.6.5 to v2.6.4 (the KV pool to ~3.4-3.7M tokens); unsetting `DSV41_TOKENIZER_HEAP` drops the heap trim; `DSV41_LOOP_NAMED_EXIT=0` / `DSV41_HISTORY_REPAIR=0` restore v2.6.4's loop exit and the HTTP 400. Unsetting `DSV41_SWA_CONE_REPLAY` / `DSV41_SWA_CONE_TOKENS` returns a lost resume point to the stock re-prefill; unsetting `DSV41_SWA_THIN` and setting `--swa-prefix-tails 128` returns the prefix cache to v2.6.3 (and the full KV pool to ~5.0-5.1M tokens; 256 is the middle step). Unsetting `DSV41_DECODE_YIELD` returns to the stock prefill / decode cadence (only the `--prefill-decode-interval 2` steps between chunks); unsetting `DSV41_SWA_NATIVE_DECODE` as well returns to the v2.6.3 profile; unsetting `DSV41_BLOCK_VERIFY_FOLD` and `DSV41_ROCE_IDLE_PARK` as well returns to the v2.6.2 profile (the #7676 fence stays in the image; it has no switch). Unsetting `DSV41_ROCE_TWOSHOT`, `DSV41_MOE_LAUNCH_PREPARED` and `DSV41_INDEXER_NOSYNC` returns to the v2.5 profile. Upstream's profile: `MAX_RUNNING_REQUESTS=8`, `CHUNKED_PREFILL_SIZE=1024`, `EXTRA_CONTAINER_ENV=""` (and `EP_SIZE=4`, `DSV41_CACHE_GIB=0` for the exact upstream example). The adapters stay in the image but do nothing when their gate is unset.

## Known limits

- The numbers above are on a switched RoCE fabric. On a switchless ring RoCEnante needs a path to the opposite node, built in the neighbours' ConnectX-7 hardware ([docs/switchless-ring.md](docs/switchless-ring.md#rocenante-on-the-ring-hardware-forwarded-opposite-node-paths)); without it the collectives go through NCCL and decode is slower. Prefill is lower on a ring either way (one-link bisection).
- The EP1 production line needs the `Dockerfile.canary-roce` image (it carries `runtime/b12x_next`). The routed MoE on b12x is numerically equivalent to FlashInfer's, not bit-identical (relative error against an fp32 reference 4.5–4.8 % for both); qeval and the needle tests are unchanged.
- Prompt-token logprobs and all-token hidden states are not available: `boot.py` launches with `--enable-decoder-swa-bounded-replay` (Mia's recipe), so the 19 layers after the last KV-source layer run only over the last 128 rows of each prefill, and such requests get HTTP 400. Output logprobs work. Cache hits are exact: a hit that lands on a prefill chunk boundary gives bit-identical logprobs to a cold request; a hit elsewhere computes the tail with a different batch shape, which moves low-probability logprobs by the same amount as the run-to-run nondeterminism of cold prefills on some prompts (`scripts/prefix_scan.py`, `docs/results/validation-20260929-v23.txt`).
- The full KV pool is pinned at 8,541,952 tokens (v41n, fraction 0.85), which leaves the head less free host memory: its lowest MemAvailable was 5.72 GiB in the memory ladder with eight 1M-token prompts resident at once, a cold 1M prefill and a long-prompt soak (2 NVRM out-of-memory log lines on two workers in that cell), and 7.15 GiB in the release gate, against 8.9-9.3 GiB with a 5.13M pool at 0.78; the fraction 0.85 also leaves the 8192-token prefill chunk less spare memory. Measured only for the ladder's and the gate's workloads. If the head runs short, 8,000,000 at 0.85 (low-water 5.96 GiB in the ladder) is the next step down, and the v2.6.4 values (see [Rollback](#rollback)) give ~3.4-3.7M tokens. Since v2.6.4 the SWA prefix-tail reserve is 384 tails (182,784 slots, ~4.1 GiB per rank); a session that forks from an older turn boundary (an edit or rewind) falls back further under SWA pressure than with 128, because superseded checkpoints are evicted first. Never raise the chunk to 16384: at 1M it took a worker to 2.5 GiB available and hung the node on another fleet.
- One of the eight v2.4 boots on 2026-10-12 hung in the server's internal warm-up request and was restarted by the boot timeout; the retry and the seven other boots were clean.
- Single-stream prose speed is bounded by DSpark acceptance (~3 accepted tokens per step on prose against ~6 on code); no configuration changes that.
- The fast loader leaves the KV pool 3–13 % smaller than the stock loader (6.7–7.3 M vs 7.5–7.8 M tokens) and more variable between boots; `DSV41_FAST_LOAD=0` restores it at ~220 s per boot ([docs/fast-load.md](docs/fast-load.md)).
- RoCEnante is a new transport in the decode path; b12x has one open report of a rank wedging under long mixed-context traffic on an earlier revision ([b12x#313](https://github.com/local-inference-lab/b12x/issues/313)). The overlay's result-boundary health check fails the step instead of hanging, and NCCL is one env change away.
- The decode yield (`DSV41_DECODE_YIELD=33`) lengthens a long prompt's prefill while other streams decode (x1.47 at 500K beside two streams). A short request (<= 256 fresh tokens) that arrives during a yield waits for the yield to end before its solo pass, and a longer follow-up queued behind the long prompt waits for the whole, longer prefill. Its cost model was fitted to one production boot's log; the share reached is what the fleet measurement shows, not a guarantee for other batch sizes.
- The lost-resume-point replay (`DSV41_SWA_CONE_REPLAY`) needs the whole 8192-token chunk budget in its first step: next to a co-batched prefill, or with a smaller chunk, it falls back to the stock re-prefill (a `DSV41_SWA_CONE revert` line). An internal invariant violation stops the engine on every rank rather than serving a replay outside its exactness argument. Its engine functions are sha256-pinned; on drift it does not install (stock behaviour, logged).
- The two-shot all-reduce is measured on a switched fabric only and is not available with `DSV41_ROCE_RING=1`; on the ring leave `DSV41_ROCE_TWOSHOT` unset.
